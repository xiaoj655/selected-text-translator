## Context

当前 `src/content.js` 的翻译卡片使用固定 `CARD_WIDTH_PX = 300`，并且只定义最小高度，不限制最大高度。译文较长时卡片会持续增高，导致可视区域外内容不可达。与此同时，固定宽度无法覆盖不同文本长度和用户阅读偏好。

本次改动聚焦在内容卡片本身：支持在卡片上直接拖拽调整宽度，并将结果持久化。这样用户不需要进入额外设置页面即可即时调整阅读区域。

## Goals / Non-Goals

**Goals:**
- 为翻译卡片增加视口安全的最大高度约束，超限时可纵向滚动。
- 让用户可直接在结果卡片上拖拽调整宽度。
- 将拖拽后的宽度持久化，并在后续卡片渲染时自动使用。
- 对拖拽结果应用最小/最大宽度限制，避免布局破坏。

**Non-Goals:**
- 不调整翻译请求协议、触发器逻辑或背景脚本翻译流程。
- 不新增 popup 宽度输入项或额外设置页面。
- 不实现按网站/按域名独立宽度配置（本次为全局宽度设置）。

## Decisions

1. 卡片高度采用视口上限 + 内部滚动
- Decision: 在卡片样式中增加 `max-height`（基于视口安全边距）和 `overflow-y: auto`，并限制横向溢出。
- Rationale: 最小改动解决长文本溢出，同时保持现有结构与定位策略。
- Alternative considered: 只让译文块滚动；源文较长时仍可能导致整卡超高。

2. 宽度调整通过卡片拖拽交互完成
- Decision: 在结果卡片提供明确的可拖拽宽度调整交互（例如右侧 resize handle 或 CSS resize 受控方案），拖动时实时更新宽度。
- Rationale: 用户操作路径最短，所见即所得，符合“直接拖动结果卡片改宽度”的需求。
- Alternative considered: popup 数字输入；不符合期望交互且操作成本更高。

3. 拖拽结果持久化到 `chrome.storage.sync`
- Decision: 拖拽结束后将宽度写入存储，并在卡片初始化时读取；无有效值时回退默认宽度。
- Rationale: 满足跨页面/会话保持一致的体验。
- Alternative considered: 仅内存态保存；页面刷新或切换后会丢失用户调整结果。

4. 保持既有定位算法，只使用“最终生效宽度”参与定位
- Decision: 延续现有候选位 + overlap 评分 + clamp 逻辑，使用拖拽后并经边界约束的宽度进行定位计算。
- Rationale: 降低回归风险，确保宽度变化后仍在视口中可见。
- Alternative considered: 重写定位策略；改动面过大且非本次核心。

## Risks / Trade-offs

- [Risk] 拖拽句柄可能与卡片内文本选择/滚动操作冲突。  
  → Mitigation: 将拖拽命中区域限制在边缘/角落，避免覆盖主要文本阅读区。

- [Risk] 频繁拖动触发过多存储写入。  
  → Mitigation: 仅在拖拽结束（pointerup）时持久化，而非每次 pointermove 都写入。

- [Risk] 极端宽度导致布局难读或越界。  
  → Mitigation: 对宽度做 min/max 钳制并在运行时回退非法值。

## Migration Plan

- 无数据迁移脚本需求；仅新增一个宽度持久化键，旧用户无该值时默认宽度生效。
- 如出现交互回归，可回滚到固定宽度与无拖拽能力版本。
